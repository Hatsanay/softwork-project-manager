# แบบปรับหน้าพนักงานและบัญชีเข้าใช้งานให้รู้ว่าแก้ข้อมูลที่ไหน

สถานะ: **ร่างเพื่อให้เจ้าของระบบตรวจ · ยังไม่ได้อนุมัติเริ่มเขียนโค้ด** (18 ต.ค. 2026)

ที่มา: ผู้ใช้บอกว่า "การผูกบัญชีผู้ใช้ ใช้งานยาก" และระบุปัญหาหลักว่า "สับสนว่าข้อมูลไหนต้องแก้ที่หน้าผู้ใช้หรือหน้าพนักงาน"

อ้างอิงกติกาข้อมูลเดิม: [บัญชีเข้าระบบกับพนักงาน](2026-10-18-user-employee-link.md)

## 1. ปัญหาที่ตรวจจากโค้ด

- ฟอร์มพนักงานมีช่องเลือกบัญชีอยู่ในส่วนข้อมูลการทำงาน ส่วนหน้าดูพนักงานแสดงเพียงชื่อบัญชีที่ผูก ไม่มีส่วนจัดการบัญชีเข้าใช้งานโดยตรง
- หน้าแก้ผู้ใช้ยังแสดงช่องชื่อ นามสกุล เบอร์โทร และสาขาที่ถูกปิดไว้เมื่อผูกพนักงานแล้ว ผู้ใช้จึงเห็นข้อมูลเดิมซ้ำและต้องอ่านแถบอธิบายก่อนรู้ว่าต้องย้ายหน้า
- ชื่อและเบอร์แก้ที่พนักงาน แต่อีเมลเข้าระบบ สิทธิ์ สถานะบัญชี และรูปโปรไฟล์อยู่ฝั่งบัญชี ทำให้จำตำแหน่งแก้ไขยาก
- อีเมลติดต่อฝ่ายบุคคลกับอีเมลเข้าระบบ และรูปบัตรกับรูปโปรไฟล์มีหน้าที่ต่างกัน แต่การแยกเมนูไม่ได้ช่วยให้เข้าใจหน้าที่เหล่านี้

## 2. ผลลัพธ์ที่เสนอ

**สำหรับผู้ดูแลที่มีสิทธิ์ครบ: เปิดพนักงานคนเดียวแล้วแก้ข้อมูลพนักงานและบัญชีของคนนั้นได้จากหน้าเดียว** โดยแบ่งส่วนตามสิ่งที่จะทำ มีปุ่มบันทึกของแต่ละส่วนอย่างชัดเจน

| ส่วนในหน้าพนักงาน | ข้อมูลและการกระทำ | ข้อความกำกับที่เสนอ |
|---|---|---|
| ข้อมูลพนักงาน | ชื่อ เบอร์โทร อีเมลติดต่อ แผนก สาขา ตำแหน่ง และข้อมูลฝ่ายบุคคลเดิม | "ชื่อ เบอร์โทร และสาขาจะใช้กับบัญชีเข้าใช้งานของพนักงานคนนี้ด้วย" |
| บัญชีเข้าใช้งาน | ชื่อผู้ใช้ อีเมลเข้าใช้งาน สิทธิ์การใช้งาน สถานะบัญชี ตั้งรหัสผ่านชั่วคราว และรูปโปรไฟล์ | "ใช้สำหรับเข้าสู่ระบบและกำหนดสิ่งที่ทำได้" |
| บัตรพนักงาน | รูปสำหรับบัตรและการออกบัตรเดิม | "รูปสำหรับพิมพ์บัตรพนักงาน" |

ส่วนเงินเดือน ภาษี และข้อมูลอื่นในหน้าพนักงานใช้โครงเดิม ไม่ต้องย้ายทั้งหมดเพื่อแก้ปัญหานี้

### ชื่อช่องที่ต้องตรงกันทุกหน้า

- `emp_email`: "อีเมลติดต่อฝ่ายบุคคล" · ข้อความใต้ช่อง "ใช้ติดต่อเรื่องพนักงาน · เปลี่ยนช่องนี้ไม่เปลี่ยนอีเมลเข้าใช้งาน"
- `user_email`: "อีเมลเข้าใช้งาน" · ข้อความใต้ช่อง "ใช้เข้าสู่ระบบและกู้คืนบัญชี"
- รูปพนักงาน: "รูปบัตรพนักงาน"
- รูปบัญชี: "รูปโปรไฟล์ในระบบ" · อธิบายการใช้เป็นรูปสำรองของบัตรตามกติกาเดิม
- ปุ่มบันทึก: "บันทึกข้อมูลพนักงาน" และ "บันทึกบัญชีเข้าใช้งาน"
- เปลี่ยนชื่อเมนู "ผู้ใช้งาน" เป็น "บัญชีเข้าใช้งาน" เพื่อบอกหน้าที่ชัดเจน โดยใช้ URL และบิตสิทธิ์เดิม

### หน้าบัญชีเข้าใช้งาน

- บัญชีที่ผูกพนักงานปัจจุบัน: ชื่อ เบอร์ และสาขาเป็นข้อมูลสรุป ไม่ทำเป็นช่องกรอกที่ปิดไว้ซ้ำอีกชุด
- ผู้มี `manageEmployees` เห็นปุ่ม "แก้ข้อมูลพนักงาน" และ "จัดการบัญชีในหน้าพนักงาน" ที่เปิดส่วนตรงเป้าหมาย
- ผู้ไม่มีสิทธิ์พนักงานยังจัดการบัญชีตามสิทธิ์เดิมได้ โดยไม่ถูกบังคับให้เข้าหน้าฝ่ายบุคคลที่ตนเปิดไม่ได้
- บัญชีบุคคลภายนอกที่ไม่ผูกพนักงานยังแก้ข้อมูลของบัญชีได้ตามเดิม

### หน้าโปรไฟล์ของพนักงานเอง

- แสดงข้อมูลจากฝ่ายบุคคลเป็นส่วนสรุป พร้อม "ชื่อและเบอร์โทรมาจากข้อมูลพนักงาน · ติดต่อฝ่ายบุคคลเมื่อต้องการแก้ไข"
- ส่วนที่เจ้าของบัญชีแก้ได้ยังมีอีเมลเข้าใช้งาน รูปโปรไฟล์ และช่องทางติดต่อของบัญชีตามเดิม
- คนไม่มีสิทธิ์ฝ่ายบุคคลไม่เห็นลิงก์ที่กดแล้วได้ 403

## 3. ข้อมูลและสถานะ

- ใช้ `tb_employees.emp_user_id` และกติกาข้อมูลตัวจริงเดิม ไม่ย้ายหรือรวมตาราง ไม่คัดลอกอีเมลระหว่างสองช่องอัตโนมัติ
- ข้อมูลพนักงานยังเป็นต้นทางชื่อ เบอร์ และสาขาของบัญชีที่ผูกกับพนักงานปัจจุบัน
- บันทึกแยกตามส่วน เพื่อไม่อ้างว่าบันทึกสำเร็จทั้งหมดทั้งที่คำขอหนึ่งล้มเหลว ไม่ส่งข้อมูลของอีกส่วนที่ไม่ได้แก้
- ไม่มีบัญชีที่ผูก: แสดง "ยังไม่มีบัญชีเข้าใช้งาน" และทางเข้าการเลือกบัญชีเดิมตามสิทธิ์ปัจจุบัน
- ปิดด้วยมือ / ปิดเพราะพ้นสภาพ / ยังเข้าใช้งานได้: แสดงสถานะจริงจาก backend พร้อมเหตุผลแยกกันตามกติกาเดิม
- การสร้างพนักงานพร้อมบัญชีใหม่ในครั้งเดียวไม่ได้อยู่ในรอบนี้ เพราะผู้ใช้ระบุว่าปัญหาหลักคือความสับสนเรื่องจุดแก้ไข
- ยังไม่คาดว่าต้องเปลี่ยน schema; ถ้าพบความจำเป็นตอนออกแบบรายละเอียด ต้องเพิ่มในแบบและทำตามกติกา deploy_schema ก่อนเขียน

## 4. สิทธิ์และ API ที่เสนอ

| การกระทำ | การตรวจฝั่ง backend |
|---|---|
| ดู/แก้ข้อมูลพนักงาน | `manageEmployees` ตามเดิม |
| อ่านรายละเอียดบัญชีจากหน้าพนักงาน | `manageEmployees` และ `usersManagement` |
| แก้บัญชีหรือตั้งรหัสผ่านชั่วคราวจากหน้าพนักงาน | `manageEmployees` และ `editUsers` พร้อมกติกาจัดการคนที่สิทธิ์ไม่เกินตัวเอง |
| แก้โปรไฟล์ตัวเอง | เส้นทางและสิทธิ์ของเจ้าของบัญชีเดิม |

- ส่วนบัญชีไม่โหลดรายละเอียดบัญชีเมื่อไม่มีสิทธิ์ แสดงเพียงข้อมูลสรุปที่ endpoint พนักงานอนุญาตอยู่แล้วและข้อความ "การแก้บัญชีเข้าใช้งานต้องให้ผู้ดูแลบัญชีดำเนินการ"
- เสนอ `GET /employees/:id/account` และ `PATCH /employees/:id/account` ซึ่งหา account จากความสัมพันธ์ปัจจุบันใน backend และรับเฉพาะช่องของบัญชีที่อนุญาต ไม่ให้ client เลือก user ID อีกตัวเอง
- ย้ายกติกาจัดการบัญชีที่จำเป็นจาก controller ไป service ที่ใช้ร่วมกับหน้าบัญชีเดิม เพื่อไม่ทำกติกา role, self-access, ชื่อผู้ใช้ซ้ำ และสถานะบัญชีซ้ำสองชุด
- การบันทึกตรวจและล็อกความสัมพันธ์ใน transaction; ถ้ามีการเปลี่ยนบัญชีที่ผูกหลังเปิดหน้า ให้ตอบ 409 พร้อมข้อความโหลดใหม่ ไม่เผลอแก้อีกบัญชี
- รูปโปรไฟล์และการตั้งรหัสผ่านใช้กระบวนการเดิมผ่านส่วนแสดงผลที่ใช้ร่วมกัน และตรวจสิทธิ์จริงทุกคำขอ
- การเปลี่ยนอีเมลใช้กติกาของผู้กระทำเดิม: เจ้าของบัญชีใช้ขั้นยืนยัน OTP; การจัดการโดยผู้ดูแลต้องอ่านและรักษากติกา backend เดิม ไม่ย้ายอำนาจนี้ให้สิทธิ์ฝ่ายบุคคลอย่างเดียว
- เพิ่ม audit mapping สำหรับ endpoint ใหม่ ไม่บันทึกรหัสผ่านชั่วคราวใน log หรือข้อความ error

## 5. ความเสี่ยงและการตรวจ

- สิทธิ์ HR กลายเป็นสิทธิ์จัดการบัญชีโดยไม่ตั้งใจ: ทดสอบคนมีเฉพาะ `manageEmployees`, เฉพาะสิทธิ์บัญชี และมีครบทั้งคู่ ทั้งหน้าจอและ API 403
- แก้ข้อมูลทับกันระหว่างสองส่วน: ส่งเฉพาะช่องของส่วนที่แก้ และทดสอบการบันทึกพร้อมกันกับการเปลี่ยนบัญชีที่ผูก
- เปลี่ยนชื่อ/เบอร์แล้วข้อมูลไม่ตรงกัน: ทดสอบว่าช่องพนักงานคัดลอกไปบัญชีตามเดิม และหน้าเก่าที่เปิดค้างเปลี่ยนข้อมูลต้นทางผ่านบัญชีไม่ได้
- อีเมลสองช่องหรือรูปสองชนิดเปลี่ยนตามกันโดยไม่ตั้งใจ: ทดสอบว่าแยกตามกติกาเดิมและข้อความระบุหน้าที่ถูกต้อง
- เปิดบัญชีด้วยมือทั้งที่พ้นสภาพ: ใช้สถานะการเข้าระบบจาก backend และรักษากติกาปิดหลังวันสุดท้าย/กลับมาทำงานใหม่
- ตรวจว่าบัญชีภายนอกยังแก้ได้และพนักงานที่ไม่มีบัญชียังใช้งานฝ่ายบุคคลได้
- ทดสอบ frontend type check/ESLint, backend ตามกติกา repo ณ วันที่เริ่มลงมือ และภาพหน้าจอใหญ่/360px/400px
