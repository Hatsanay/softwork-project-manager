## 1. เปรียบเทียบวิธี (D1)

| | ก) แยก View | ข) API ปลอม | ค) ชิ้นส่วนจริง |
|---|---|---|---|
| หน้าตาตรงหน้าจริง | 100% (JSX เดียวกัน) | 100% | ~85–90% (layout ของหน้ายังเขียนเอง) |
| แก้หน้าจริงแล้วเดโมเปลี่ยนตาม | ✅ อัตโนมัติ | ✅ | ⚠️ เฉพาะชิ้นส่วนที่ใช้ร่วม |
| แตะหน้าจริง | ⚠️ แยกไฟล์ทีละหน้า (พฤติกรรมเดิม) | ⚠️ ต้องเปลี่ยน `next/navigation` ใน ~74 ไฟล์ + ดัก apiFetch | ✅ ไม่แตะ |
| เดโมยังเป็น "ฟังก์ชันของเวลา t" (กดข้ามขั้น / ย้อน / ลดการเคลื่อนไหว ทำงานถูก) | ✅ | ❌ state อยู่ในหน้าจริง ข้ามขั้นต้องเล่นซ้ำตั้งแต่ต้น | ✅ |
| ความเสี่ยงพัง | ต่ำ — ข้อมูลตัวอย่างใช้ type เดียวกับหน้า (`_types.ts`) tsc จับได้ทันทีเมื่อ API เปลี่ยน | สูง — API ปลอมต้องตอบเหมือน backend ~30 จุด เปลี่ยนเมื่อไหร่พังเงียบ · toast/redirect หลุดออกนอกจอเดโม | ต่ำ |
| ได้ประโยชน์อื่น | หน้าจริงอ่านง่ายขึ้น (โหลดข้อมูล/แสดงผลแยกกัน) ทดสอบ View ได้ | — | — |
| งาน | มาก (ทำทีละหน้าได้) | มากที่สุด | ปานกลาง |

**ทำไมแนะนำ ก:** ได้ "หน้าจริง" จริงตามที่สั่ง และระยะยาวดูแลง่ายที่สุด · ข เสี่ยงและเปราะเกินไปสำหรับหน้า login · ค ไม่ตอบโจทย์ "หน้าจริง"

### ข้อเท็จจริงที่ตรวจแล้ว (ทำให้ ก ทำได้)

- **breakpoint:** จอเสมือนกว้าง 1024px และเดโมแสดงเฉพาะจอจริงกว้าง ≥1024px (lg) → class `sm:` `md:` `lg:` ของหน้าจริงทำงานแบบจอคอมตรงกัน · หน้าเป้าหมายทั้งหมด**ไม่มี** `xl:`/`2xl:` (ตรวจแล้ว 0 จุด) → layout ไม่เพี้ยน
- **หน้าต่างลอย:** ConfirmDialog / ชีตด้านข้างใช้ `fixed inset-0` — อยู่ใต้กล่องที่มี `transform: scale()` แล้ว `fixed` จะยึดกับจอเสมือนเอง (บังเฉพาะจอเดโม ไม่บังหน้า login) ✅
- **สิทธิ์:** ปุ่มในหน้าเอกสารอ่านจาก `actions` ที่ backend ส่งมา (`can_approve`, `can_receive` …) → ข้อมูลตัวอย่างกำหนดเองได้ ไม่ต้องใช้ PermissionProvider ในส่วน View
- **ส่วนที่แยกไว้แล้ว:** การ์ดแดชบอร์ด, คอลัมน์/การ์ดบอร์ดงาน, ShareLinkCard, ApprovalProgress, SummaryPanel, PermissionChecklist ไม่โหลดข้อมูลเอง ใช้ได้ทันที

## 3. โครงสร้าง (ถ้าเลือก D1-ก)

- **หน้าจริง:** `page.tsx` = โหลดข้อมูล + จัดการกดปุ่ม → ส่งให้ `_components/<name>-view.tsx` (รับ props อย่างเดียว ไม่เรียก API ไม่ใช้ router ไม่เรียก toast)
  - ฟอร์ม: ค่าในช่อง + error + ฟังก์ชัน onChange มาจาก props (เดโมส่งค่าที่ "กำลังพิมพ์" ตามเวลา t)
  - ปุ่ม: View รับ `onApprove` ฯลฯ — เดโมส่งฟังก์ชันว่าง · ใส่ `data-demo="..."` ที่ปุ่มให้เมาส์เดโมหาเจอ (ไม่มีผลกับหน้าจริง)
- **แถบเมนู/แถบบน:** แยก `SidebarNav` และ `NavbarView` ที่รับ `pathname` เป็น prop (ตอนนี้อ่าน `usePathname()` ซึ่งบนหน้า login คืนค่า /login)
- **ข้อมูลตัวอย่าง:** `system-demo/fixtures/*.ts` ใช้ type จาก `_types.ts` ของแต่ละหน้า · ยอดเงินเป็นสตริงแบบที่ API ส่ง (ผ่าน formatAmount ตัวจริง) · เรื่องเดียวกันทั้งชุด
- **ตัวเล่น:** ใช้ของเดิม (player.ts, desktop-screen.tsx — นาฬิกา, เมาส์, จอ) · เมาส์ชี้ปุ่มในหน้าจริงด้วย `css:` / `text:` (ไม่ต้องใส่ data-demo ในหน้าจริง) · ช่วงของงานแสดงในคำอธิบายใต้หัวข้อ
- **ขนาดหน้า login:** โหลดเดโมแบบ dynamic import หลังฟอร์ม login แสดงแล้ว (ฟอร์มไม่ช้าลง)
