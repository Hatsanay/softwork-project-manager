# แผนแม่บท: พัฒนาเป็น ERP เต็มระบบ (เริ่ม 8 ต.ค. 2026 · ระยะใช้งานเป้าหมาย 20+ ปี)

สถานะ: **เฟส 1 วงจรขายเสร็จ (16 ต.ค. 2026)** — [2026-10-08-sales-cycle.md](2026-10-08-sales-cycle.md) · **เฟส 2 จัดซื้อ/ค่าใช้จ่ายเสร็จ (17 ต.ค. 2026)** — [2026-10-16-purchasing-2.md](2026-10-16-purchasing-2.md) (รอคำตอบนักบัญชี X1–X6 ก่อนใช้จริง)

## เป้าหมาย
ระบบเดียวที่ใช้ได้ทุกแผนก: ขาย (ใบเสนอราคา → วางบิล → ใบกำกับภาษี → รับเงิน), จัดซื้อ/ค่าใช้จ่าย, ภาษี,
บัญชี, บุคคล/เงินเดือน, ผู้ถือหุ้น/ปันผล — ต่อยอดจากระบบบริหารโปรเจกต์ที่มีอยู่ (โปรเจกต์ = ศูนย์กลางของงานขายและต้นทุน)

## หลักการออกแบบที่ต้องตัดสินใจตั้งแต่วันแรก (แก้ทีหลังแพงมาก)

1. **บัญชีคู่ (double-entry) เป็นแกนกลาง** — ทุกเอกสารที่เกี่ยวกับเงิน (ใบกำกับ, ใบเสร็จ, ค่าใช้จ่าย, เงินเดือน, ปันผล)
   ต้องลงรายการบัญชี (journal) เข้าบัญชีแยกประเภท (GL) ที่เดียว รายงานทุกตัว (งบกำไรขาดทุน, งบดุล, ภาษี) อ่านจาก GL
   — ไม่ใช่ต่างโมดูลต่างคำนวณกำไรเอง (บทเรียนจาก fasttiw: ส่วนแบ่งกำไรเกือบถูกหักซ้ำ เพราะไม่มี ledger กลาง)
2. **เอกสารที่ออกแล้วแก้ไม่ได้** — ใบกำกับภาษี/ใบเสร็จที่ออกแล้วห้ามแก้หรือลบ ทำได้แค่ยกเลิก (void) หรือออกใบลดหนี้/ใบเพิ่มหนี้
   เลขที่เอกสารต้องเรียงต่อเนื่อง ไม่ข้าม ไม่ซ้ำ แยกตามประเภทเอกสาร/ปี (ข้อกำหนดของกรมสรรพากร)
3. **เงินใช้ DECIMAL เสมอ ห้าม float** · กติกาปัดเศษ (ภาษีต่อบรรทัด vs ต่อเอกสาร) กำหนดที่เดียว มีเทสต์อัตโนมัติครอบ
4. **อัตราภาษี/ประกันสังคม/เพดานต่างๆ เก็บเป็นตารางพร้อม "วันที่มีผล"** ไม่ hardcode — 20 ปีอัตราเปลี่ยนหลายรอบแน่นอน
   และการคำนวณย้อนหลังต้องใช้อัตรา ณ วันนั้น
5. **ปิดงวดบัญชี (period lock)** — ปิดเดือน/ปีแล้วห้ามมีรายการใหม่ย้อนเข้าไป (แก้ได้ด้วยรายการปรับปรุงในงวดปัจจุบันเท่านั้น)
6. **รองรับหลายบริษัท (company_id) ตั้งแต่โครงสร้างแรก** — ถ้า 20 ปีมีบริษัทลูก/สาขา การเพิ่มทีหลังต้องแก้ทุกตาราง
7. **ระบบสิทธิ์ต้องเปลี่ยน** — bitmask string ปัจจุบัน (27 บิต, VARCHAR(64), append-only) จะไม่พอสำหรับ ERP ที่มีสิทธิ์หลายร้อยรายการ
   → ย้ายเป็นตารางสิทธิ์แบบรหัส (permission code) + สิทธิ์ระดับแผนก/ระดับวงเงินอนุมัติ
8. **ข้อมูลใช้ได้ 20 ปี** — audit log มีแล้ว, ระยะเก็บเอกสารบัญชีตามกฎหมาย (อย่างน้อย 5–7 ปี — ยืนยันกับนักบัญชี),
   backup อัตโนมัติ + ทดสอบกู้คืน, ส่งออกข้อมูลเป็นรูปแบบเปิดได้เสมอ (ไม่ขังข้อมูลไว้ในระบบ)
9. **ทุกเงื่อนไขต้องอธิบายบนหน้าจอ — ทั้งระบบ ทุกหน้า ทุกเรื่อง** (ผู้ใช้สั่ง 12 ต.ค. 2026) — ไม่ใช่แค่การอนุมัติ:
   กติกา/ข้อจำกัด/การล็อก/สิทธิ์/การคำนวณ ต้องมีข้อความภาษาไทยง่ายๆ ตามรูปแบบใน [2026-10-12-ui-guidance.md](2026-10-12-ui-guidance.md)
   (**ห้าม tooltip** — ข้อความใต้ช่อง, "ทำงานอย่างไร?" กางในที่, แถบสถานะเหนือปุ่มบอกเหตุผลที่ทำไม่ได้), error บอก "ทำไม + ต้องทำอะไรต่อ" · ทุกแบบโมดูลต้องมีหัวข้อ "ข้อความกำกับ" พร้อมถ้อยคำจริง
   · หน้าเดิมที่ยังไม่มี (ผู้ใช้, role, แผนก, โปรเจกต์, งาน, issue, ลูกค้า, ตั้งค่า, log) เติมเมื่อแก้หน้านั้น หรือทำรวดเดียว (ดูเฟส 0)

## ความเสี่ยงที่ต้องพูดตรงๆ
- **ความถูกต้องตามกฎหมายภาษีและบัญชี** คือความเสี่ยงอันดับหนึ่ง — ต้องมีนักบัญชี/ผู้สอบบัญชีของบริษัทตรวจรับแต่ละเฟส
  (โดยเฉพาะผังบัญชี, รูปแบบใบกำกับภาษี, การคำนวณภาษีเงินเดือน) ตัวเลขอัตราต่างๆ ในแผนนี้ต้องยืนยันกับนักบัญชีก่อนใช้จริง
- **ทางเลือกที่ควรชั่งก่อน**: โปรแกรมบัญชีสำเร็จรูปของไทย (ซึ่งรับผิดชอบเรื่องกฎหมายให้) + เชื่อมต่อกับระบบนี้
  vs สร้างบัญชีเองทั้งหมด — สร้างเองได้ความยืดหยุ่นเต็มที่ แต่ต้องดูแลการเปลี่ยนแปลงกฎหมายเองไปตลอด 20 ปี
- **โครงสร้างพื้นฐาน**: Plesk shared hosting + process เดียว เหมาะกับระบบตอนนี้ แต่ ERP ที่ทั้งบริษัทพึ่งพาควรมี
  backup อัตโนมัติที่ทดสอบกู้คืนแล้ว, สภาพแวดล้อมทดสอบ (staging) แยกจาก production, และแผนรองรับเมื่อเซิร์ฟเวอร์ล่ม
- **หนี้ทางเทคนิคที่ต้องแก้ก่อนขยาย**: ไม่มีเทสต์อัตโนมัติ (เทสต์ตอนนี้อยู่นอก repo), หน้าเว็บบางหน้าใหญ่ 2,800 บรรทัด,
  token อยู่ใน localStorage — แก้ในเฟส 0

## การตัดสินใจ (8 ต.ค. 2026)
- ระบบบริหารภายใน ส่งข้อมูลต่อให้นักบัญชี (ยังไม่ทำบัญชีแยกประเภททางการ — หลักการข้อ 1 "บัญชีคู่" เลื่อนออกไป แต่ข้อมูลเงินทุกตัวต้องออกแบบให้ลงบัญชีย้อนหลังได้)
- ยังไม่จด VAT คาดว่าจดใน ~1 ปี → VAT เปิดตามวันที่มีผล
- บริษัทเดียว อาจมีศูนย์บริการหลายแห่ง → ใช้ "สาขา" แทน "หลายบริษัท" (หลักการข้อ 6 เปลี่ยนเป็น branch_id)
- เริ่มที่วงจรขาย

## เรื่องที่เคยถาม
1. ระบบนี้จะเป็น **บัญชีทางการ** ที่ส่งงบ/ภาษีจริง หรือเป็นระบบบริหารภายในแล้วส่งข้อมูลให้นักบัญชี/โปรแกรมบัญชี
2. บริษัท **จดทะเบียนภาษีมูลค่าเพิ่ม (VAT)** หรือยัง
3. มีแผน **หลายบริษัท/สาขา** ไหม
4. เริ่มเฟสไหนก่อนหลังเฟส 0 (แนะนำ: วงจรขาย — ผูกกับโปรเจกต์ที่มีอยู่และใช้ทุกวัน)
