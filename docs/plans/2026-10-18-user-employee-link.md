## 0. สิ่งที่คงไว้ (ไม่แก้)

- แยกตาราง `tb_users` (บัญชีเข้าระบบ) กับ `tb_employees` (ทะเบียนบุคคล) และผูกแบบไม่บังคับด้วย `emp_user_id`
  - มีบัญชีแต่ไม่ใช่พนักงาน: ฟรีแลนซ์ นักบัญชีภายนอก ผู้ตรวจสอบ
  - เป็นพนักงานแต่ไม่มีบัญชี: แม่บ้าน คนขับรถ ช่างหน้างาน
  - สิทธิ์ดูข้อมูลเงินเดือน/เลขบัตรประชาชนต้องแยกจากข้อมูลบัญชี
- ชื่อผู้ทำรายการที่ snapshot ไว้บนเอกสารเก่า (`*_created_by_name` ฯลฯ) ไม่เปลี่ยนย้อนหลัง

## 1. ข้อมูลตัวจริงที่เดียว

**หลัก:** บัญชีที่ผูกกับ "พนักงานปัจจุบัน" แล้ว ข้อมูลที่เป็นเรื่องเดียวกันให้พนักงานเป็นตัวจริง ระบบคัดลอกไปที่บัญชีให้เอง (แก้ที่หน้าพนักงานที่เดียว)

| ข้อมูล | ตัวจริง | หน้าบัญชีผู้ใช้ / โปรไฟล์ | เหตุผล |
|---|---|---|---|
| ชื่อ-สกุล | **พนักงาน** `emp_first_name_th` / `emp_last_name_th` → `user_fname` / `user_lname` | อ่านอย่างเดียว + "แก้ที่หน้าพนักงาน (ฝ่ายบุคคล)" | ชื่อตามกฎหมาย ใช้บนสลิป ภ.ง.ด. 50 ทวิ |
| เบอร์โทร | **พนักงาน** `emp_phone` → `user_phone` | อ่านอย่างเดียว | เบอร์เดียวกัน |
| สาขา | **พนักงาน** (สาขาของแผนก) → `user_branch_id` | อ่านอย่างเดียว | สาขาของพนักงานมาจากแผนกแล้ว (ระบบรหัส 2026-10-18) |
| อีเมล | **แยกกัน** | แก้ได้เหมือนเดิม (ยืนยัน OTP) | `user_email` = ตัวตนสำหรับเข้าระบบและรีเซ็ตรหัสผ่าน · ถ้าฝ่ายบุคคลแก้ได้ = ทางยึดบัญชี · `emp_email` เปลี่ยนชื่อช่องเป็น "อีเมลติดต่อ (ฝ่ายบุคคล)" |
| รูป | **แยกกัน** | แก้ได้เหมือนเดิม | รูปโปรไฟล์ (สี่เหลี่ยมจัตุรัส ตั้งเอง) กับรูปบัตร (3:4 ทางการ) ใช้คนละแบบ · บัตรใช้รูปโปรไฟล์แทนเมื่อไม่มีรูปบัตรอยู่แล้ว |
| LINE / WhatsApp | บัญชี | แก้ได้เหมือนเดิม | ช่องทางแจ้งเตือนของบัญชี |

**"พนักงานปัจจุบัน" ของบัญชี** = แถวที่ผูกกับบัญชีนี้และยังไม่พ้นสภาพ (`emp_termination_date` ว่างหรือ ≥ วันนี้) · ระบบห้ามผูกบัญชีเดียวกับพนักงานที่ยังทำงานอยู่สองคนอยู่แล้ว
- บัญชีที่ผูกกับพนักงานที่พ้นสภาพแล้วเท่านั้น (ไม่มีแถวปัจจุบัน) → ช่องในบัญชีกลับมาแก้ได้ (เช่น กลายเป็นที่ปรึกษาภายนอก)

**การคัดลอก (ใน transaction เดียวกับการบันทึกพนักงาน · ล็อกแถวบัญชีด้วย)**
- เพิ่มพนักงาน / แก้ข้อมูลพนักงาน / ย้ายแผนก-สาขา / เปลี่ยนบัญชีที่ผูก → คัดลอกชื่อ เบอร์ สาขา ไปที่บัญชี (ถ้าแถวนี้เป็นพนักงานปัจจุบัน)
- เลิกผูกบัญชี → บัญชีคงค่าล่าสุดไว้ แล้วกลับมาแก้เองได้
- ฝั่งบัญชี (แอดมินแก้ผู้ใช้ · ผู้ใช้แก้โปรไฟล์ตัวเอง): ถ้ามีพนักงานปัจจุบัน backend **ไม่รับค่าที่ส่งมา** ในช่องชื่อ/เบอร์/สาขา (ใช้ค่าจากพนักงานแทน) — หน้าเว็บปิดช่องไว้แล้ว กันหน้าเก่าที่ยังเปิดค้าง

## 2. ปิดการเข้าระบบเมื่อพ้นสภาพ

- หน้าต่าง "ตั้งพ้นสภาพ" (เมื่อพนักงานผูกบัญชีที่ยังใช้งานอยู่): ช่องติ๊ก **"ปิดการเข้าระบบของบัญชี {username} หลังวันทำงานวันสุดท้าย"** (ค่าเริ่ม = ติ๊ก)
- เก็บเป็นคอลัมน์ของพนักงาน `emp_close_login_on_termination` (ไม่ตั้ง `user_status` ตอนกดบันทึก) เพราะ
  - วันสุดท้ายตั้งล่วงหน้าได้ และ hosting (Plesk) ไม่มีงานตั้งเวลา → ตรวจตอนเข้าระบบ/ทุกคำขอแทน (auth middleware อ่านแถวผู้ใช้ทุกคำขออยู่แล้ว)
  - เลื่อนวันพ้นสภาพ / ยกเลิกการพ้นสภาพ → การปิดเลื่อน/ยกเลิกตามเอง ไม่ต้องไปแก้บัญชีอีกที่
- **กติกาปิด:** บัญชีเข้าไม่ได้เมื่อ **ไม่มีพนักงานปัจจุบัน** และ **มีพนักงานที่พ้นสภาพแล้ว (วันสุดท้าย < วันนี้ เวลาไทย) ที่ติ๊กปิดไว้**
  - "ไม่มีพนักงานปัจจุบัน" กันกรณีกลับมาทำงานใหม่ (แถวพนักงานใหม่ผูกบัญชีเดิม) แล้วโดนแถวเก่าปิด
  - วันทำงานวันสุดท้ายยังเข้าได้ทั้งวัน · ปิดตั้งแต่ 00:00 ของวันถัดไป (เวลาไทย)
- ที่ต้องตรวจ: login (`auth.controller`) · ทุกคำขอ (`auth.middleware` — token ที่ออกก่อนหน้าใช้ต่อไม่ได้) · ข้อความ "บัญชีนี้ปิดแล้วเพราะพ้นสภาพพนักงานเมื่อ {วันที่} · ติดต่อฝ่ายบุคคล"
- แสดงผล
  - หน้าพนักงาน: "เข้าระบบได้ถึง {วันสุดท้าย}" / "ปิดการเข้าระบบแล้ว" + ปุ่ม "เปิดให้เข้าระบบต่อ" (ยกเลิกติ๊ก — สิทธิ์ `manageEmployees`)
  - หน้าผู้ใช้ (รายการ/ดู): ป้าย "ปิดเพราะพ้นสภาพ" แยกจาก "ปิดใช้งาน" (`user_status`)
  - แถบเตือน "บัญชีผู้ใช้ยังเข้าระบบได้" ในหน้าพนักงานเดิม: แสดงเฉพาะกรณีไม่ได้ติ๊กปิด
- เปิดใหม่ทีหลังได้เสมอ (ยกเลิกติ๊ก / ยกเลิกพ้นสภาพ / เลิกผูก) · `user_status` ยังใช้ปิดบัญชีด้วยมือได้เหมือนเดิม

## 3. ข้อมูล

| ตาราง | เปลี่ยน |
|---|---|
| `tb_employees` | + `emp_close_login_on_termination` tinyint(1) NOT NULL DEFAULT 1 |
| `tb_users` | ไม่เพิ่มคอลัมน์ |

**deploy (รันซ้ำได้)**
1. เพิ่มคอลัมน์ (พนักงานที่พ้นสภาพอยู่แล้ว: ค่า = **0** — ไม่ปิดบัญชีใครเองตอน deploy · ดู K3)
2. คัดลอกชื่อ/เบอร์/สาขาจากพนักงานปัจจุบันไปที่บัญชีที่ผูก (ดู K2) · ก่อนรัน ให้ดูรายการที่จะเปลี่ยนด้วย query ตรวจ (แนบในไฟล์ deploy เป็นหมายเหตุ)

## 4. หน้าจอ

- **ผู้ใช้ › แก้ไข** และ **โปรไฟล์**: ช่องชื่อ เบอร์ สาขา เป็นอ่านอย่างเดียวเมื่อผูกพนักงานปัจจุบัน · แถบ "ข้อมูลนี้มาจากทะเบียนพนักงาน {รหัส} · แก้ที่หน้าพนักงาน" (ลิงก์เฉพาะคนที่มีสิทธิ์จัดการพนักงาน · คนอื่นเห็น "ติดต่อฝ่ายบุคคล")
- **ผู้ใช้ › ดู / รายการ**: แสดง "ผูกกับพนักงาน {รหัส} {ชื่อ}" + ป้ายสถานะการเข้าระบบ
- **พนักงาน › ฟอร์ม**: ช่องบัญชีผู้ใช้บอกว่า "ชื่อ เบอร์ สาขาของบัญชีจะเปลี่ยนตามพนักงาน" · `emp_email` ชื่อช่อง "อีเมลติดต่อ"
- **พนักงาน › ตั้งพ้นสภาพ**: ช่องติ๊กปิดการเข้าระบบ (ข้อ 2)
- **พนักงาน › หน้าพนักงาน**: สถานะการเข้าระบบของบัญชีที่ผูก + ปุ่มเปิดต่อ

## 6. เทสต์

- แก้ชื่อ/เบอร์/ย้ายแผนกพนักงาน → บัญชีที่ผูกเปลี่ยนตาม · บัญชีที่ไม่ผูกไม่เปลี่ยน
- แก้ชื่อที่หน้าผู้ใช้/โปรไฟล์ของบัญชีที่ผูกพนักงานปัจจุบัน → ค่าไม่เปลี่ยน · เลิกผูกแล้วแก้ได้
- พ้นสภาพล่วงหน้า + ติ๊กปิด → วันสุดท้ายยังเข้าได้ · วันถัดไป login ไม่ได้และ token เดิมได้ 401 พร้อมข้อความ
- ยกเลิกพ้นสภาพ / ยกเลิกติ๊ก → เข้าได้อีก
- กลับมาทำงานใหม่ (แถวใหม่ผูกบัญชีเดิม) → เข้าได้ (R1)
- ผู้ดูแลระบบคนสุดท้าย → ติ๊กปิดไม่ได้ (R4)
- deploy: ฐานใหม่ · อัปเกรดซ้ำ 2 รอบ · พนักงานที่พ้นสภาพอยู่แล้วไม่ถูกปิดบัญชี
