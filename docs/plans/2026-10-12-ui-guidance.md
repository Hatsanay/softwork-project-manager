# แนวทาง UI: อธิบายกติกาให้ผู้ใช้เข้าใจ (ทั้งระบบ) — 12 ต.ค. 2026

สถานะ: **ผู้ใช้เลือกแนวทางแล้ว** — ใช้กับทุกหน้า ทุกโมดูล (หน้าเดิม + ERP ทุกเฟส)
ที่มา: ผู้ใช้สั่งให้ทุกหน้าที่มีเงื่อนไขมีข้อความกำกับ และ **ไม่ใช้ tooltip ("ดูเชยเกินไป")**

## กฎเหล็ก
1. **ห้ามใช้ tooltip ทุกแบบ** — ทั้ง `title=""` และ popup ตอนชี้เมาส์ · เหตุผลเพิ่ม: บนมือถือ/แท็บเล็ตไม่มีการชี้ค้าง ข้อมูลจะไม่มีวันถูกเห็น
   **ข้อยกเว้นเดียว** (ผู้ใช้เลือก 12 ต.ค. 2026): ชื่อเมนูที่ขึ้นตอนชี้ไอคอนในแถบข้างที่ย่ออยู่ — เป็นแค่ชื่อเมนู (กางแถบก็เห็น) ไม่ใช่กติกา
   (หน้าเดิมที่ยังใช้ `title=""`: clients, projects, projects/view, settings/departments, settings/project-positions — เปลี่ยนในรอบเติมข้อความกำกับหน้าเดิม)
2. **ข้อมูลสำคัญต้องเห็นได้โดยไม่ต้องชี้/เดา** — อ่านจากหน้าจอได้เลย หรือกดหนึ่งครั้งแล้วกางในที่
3. **ทุกข้อความตอบ 2 คำถาม:** ทำไม + ต้องทำอะไรต่อ (หรือรอใคร)
4. **toast ใช้เฉพาะแจ้งสำเร็จ** — ข้อผิดพลาด/เหตุผลที่ทำไม่ได้ต้องอยู่บนหน้าจนกว่าจะแก้ (toast หายเองก่อนอ่านทัน)
5. ข้อความทั้งหมดของโมดูลเก็บในไฟล์ข้อความไฟล์เดียว (แก้ถ้อยคำที่เดียว)

## ธีม (ผู้ใช้สั่ง "ห้ามหลุดธีม" 12 ต.ค. 2026)
ใช้เฉพาะสีที่ระบบมีอยู่: Tailwind gray (พื้น gray-50, การ์ดขาวขอบ gray-100, ช่องกรอกขอบ gray-300) · ปุ่มหลัก blue-500/hover blue-600 · พื้นอ่อน blue-50 ·
สถานะ green/amber/red-600 บนพื้น -50 · สีถ่านของโลโก้ · ฟอนต์ Kanit (หัวข้อ 500) · ทำให้ทันสมัยด้วยการจัดวาง/ส่วนประกอบ ไม่ใช่สีใหม่

## รูปแบบมาตรฐาน 6 แบบ (สร้างเป็น component กลางใน `frontend/components/ui/guidance/`)

### 1. `FieldHint` — ข้อความสั้นใต้ช่อง (เห็นตลอด)
```
อัตรา VAT (%)   [ 7.00 ]
ใช้กับเอกสารที่ลงวันที่ตั้งแต่วันจด VAT เป็นต้นไป · เอกสารเก่าไม่เปลี่ยน
```
- 1–2 บรรทัด สีเทา ตัวเล็ก · ถ้าช่องมี error ข้อความเปลี่ยนเป็นสีแดงพร้อมบอกวิธีแก้แทนที่ ณ ตำแหน่งเดิม

### 2. `HowItWorks` — ลิงก์ "ทำงานอย่างไร?" กดแล้วกางในที่ (แทนไอคอน ⓘ)
```
ยอดขั้นต่ำชั้น 2   [ 100,000 ] บาท
ใบที่ยอดก่อน VAT ถึงเกณฑ์นี้ ต้องผ่านชั้น 2 ด้วย
▾ ทำงานอย่างไร?
│ ตัวอย่างจากกติกาที่ตั้งอยู่ตอนนี้:
│ • ใบ 50,000 บาท    → ชั้น 1
│ • ใบ 250,000 บาท   → ชั้น 1 → 2
│ • ใบ 1,500,000 บาท → ชั้น 1 → 2 → 3
```
- **ตัวอย่างคำนวณจากค่าที่ตั้งจริงตรงนั้น** (เปลี่ยนตามที่พิมพ์) ไม่ใช่ข้อความตายตัว
- ปุ่มเป็น `<button aria-expanded>` กดด้วยคีย์บอร์ด/นิ้วได้ · จำสถานะกาง/หุบต่อผู้ใช้ไม่ได้บังคับ

### 3. `StatusBanner` — แถบสถานะเหนือกลุ่มปุ่ม (ผู้ใช้เลือกแบบนี้สำหรับ "ทำไม่ได้")
```
╭───────────────────────────────────────────────╮
│ ⏳ รออนุมัติชั้น 2 จาก 3                        │
│ ผู้อนุมัติได้: ผู้จัดการ, กรรมการผู้จัดการ          │
│ คุณอนุมัติใบนี้ไม่ได้ เพราะคุณเป็นผู้สร้าง           │
│ (หลักควบคุมภายใน — คนสร้างกับคนอนุมัติต้องคนละคน) │
╰───────────────────────────────────────────────╯
[ ดาวน์โหลด PDF ]  [ คัดลอกเป็นใบใหม่ ]
```
- บอก 3 อย่าง: **สถานะตอนนี้ · รอใคร/อะไร · คุณทำอะไรได้/ไม่ได้ เพราะอะไร**
- **ปุ่มที่ผู้ใช้ทำไม่ได้ให้ซ่อน** เหลือเฉพาะปุ่มที่กดได้จริง — แต่ถ้าเป็นสิ่งที่ผู้ใช้ "น่าจะคาดว่าทำได้" (เช่น ผู้มีสิทธิ์อนุมัติแต่เป็นผู้สร้าง) แถบต้องพูดถึงเสมอ
- โทนสีตามสถานะ: ข้อมูล (ฟ้า) · รอ (เหลือง) · ติดปัญหา (ส้ม) · ปิดแล้ว/ยกเลิก (เทา) · สำเร็จ (เขียว)
- `role="status"` ให้โปรแกรมอ่านหน้าจออ่านได้ · ข้อความมาจาก backend (ฟิลด์ `guidance` ใน API) เพื่อให้ตรรกะสิทธิ์อยู่ที่เดียว ไม่ต้องคำนวณซ้ำฝั่งหน้าเว็บ

### 4. `ReadinessChecklist` — รายการ "ต้องมีอะไรก่อน" (ใช้คู่กับแถบสถานะในหน้าร่าง)
```
╭─ ก่อนส่งขออนุมัติ ──────────────────────────╮
│ ✓ มีรายการที่มีราคาอย่างน้อย 1 รายการ          │
│ ✓ ยอดรวมมากกว่า 0                         │
│ ✗ งวดชำระรวม 90% — ยังขาด 10% (5,000 บาท)   │  ← กดแล้วเลื่อนไปที่ส่วนงวดชำระ
│ ✓ ลูกค้ายังเปิดใช้งาน                        │
╰───────────────────────────────────────────╯
[ ส่งขออนุมัติ ]  ← กดได้เมื่อครบทุกข้อ
```
- อัปเดตสดขณะพิมพ์ · ข้อที่ยังไม่ผ่านกดแล้วพาไปที่ช่องนั้น · backend ตรวจซ้ำด้วยรายการเดียวกันเสมอ

### 5. `ConsequenceDialog` — หน้าต่างยืนยันที่บอกผลที่จะเกิด (ต่อยอด `ConfirmDialog` เดิม)
```
อนุมัติใบเสนอราคา
• คุณกำลังอนุมัติ ชั้น 1 และชั้น 2
• ชั้น 3 ต้องให้คนอื่นอนุมัติต่อ (ชั้นนี้กำหนดให้เป็นคนละคน)
• ยอด 1,250,000.00 บาท
                                   [ ยกเลิก ] [ อนุมัติ 2 ชั้น ]
```
- ปุ่มยืนยันพูดสิ่งที่จะเกิดจริง ("อนุมัติ 2 ชั้น", "ยกเลิกใบเสนอราคา") ไม่ใช่ "ตกลง"
- การกระทำที่ย้อนไม่ได้ต้องบอกว่า "ย้อนกลับไม่ได้" · ต้องใส่เหตุผล → ช่องกรอกอยู่ในหน้าต่างนี้

### 6. `LiveSummary` — ป้ายสรุปผลที่เปลี่ยนตามที่กรอก
```
รวมทั้งสิ้น 267,500.00 บาท
ยอดนี้ต้องอนุมัติ 2 ชั้น: หัวหน้าฝ่ายขาย → ผู้จัดการ
```
- ใช้ในฟอร์มที่ผลลัพธ์ขึ้นกับกติกา (อนุมัติ, VAT, อัตราแลกเปลี่ยน, งวดชำระ)

### เสริม: หน้าว่าง (empty state)
ตาราง/รายการที่ยังไม่มีข้อมูล → บอกว่าคืออะไร ทำไมยังว่าง และปุ่มทำขั้นแรก
เช่น "ยังไม่มีใบเสนอราคาที่รอคุณอนุมัติ — ใบที่ตรงกับ role ของคุณจะขึ้นที่นี่"

## เลือกใช้แบบไหนเมื่อไหร่
| สถานการณ์ | ใช้ |
|---|---|
| ช่องกรอกที่มีกติกา/รูปแบบ | FieldHint (+ HowItWorks ถ้ากติกาซับซ้อน) |
| ตั้งค่าที่ส่งผลกับส่วนอื่น | FieldHint + HowItWorks พร้อมตัวอย่างจากค่าจริง |
| หน้าเอกสาร/รายการที่มีสถานะ | StatusBanner เหนือปุ่ม |
| ฟอร์มที่ต้องครบเงื่อนไขก่อนส่ง | ReadinessChecklist + StatusBanner |
| การกระทำสำคัญ/ย้อนไม่ได้ | ConsequenceDialog |
| ผลลัพธ์ขึ้นกับสิ่งที่กรอก | LiveSummary |
| error จาก backend | ข้อความในที่ (ใต้ช่อง หรือในแถบสถานะ) ไม่ใช่ toast |
