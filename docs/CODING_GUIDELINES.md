# แนวทางการเขียนโค้ด Softwork

> สำหรับทุกคนที่เขียนโค้ดใน repo นี้ (คนและ AI) · เริ่มใช้ 12 ต.ค. 2026 · ภาพรวมระบบอยู่ที่ [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md)
> ระบบนี้กำลังเป็น ERP ที่ตั้งใจใช้ **มากกว่า 20 ปี** ข้อมูลเงิน ภาษี และ audit log แก้ย้อนหลังไม่ได้

## 0. หลัก 6 ข้อ
1. **ออกแบบก่อน เขียนทีหลัง** — งานใหญ่ต้องมีแบบใน `docs/plans/` และเจ้าของระบบสั่ง "เริ่มเขียนโค๊ด" ก่อน
2. **backend คือความจริง** — สิทธิ์ ยอดเงิน สถานะ เลขที่เอกสาร ตัดสินที่ backend เสมอ หน้าเว็บแค่แสดงและช่วยกรอก
3. **ห้ามมองข้ามเรื่องเล็ก** — ทุกงานต้องผ่านเช็กลิสต์หัวข้อ 11 ก่อนส่งมอบ
4. **ผู้ใช้ต้องเข้าใจกติกาก่อนกด** — ทุกเงื่อนไขมีข้อความกำกับบนหน้าจอ ไม่ใช้ tooltip ([ui-guidance](plans/2026-10-12-ui-guidance.md))
5. **อ่านโค้ดรอบๆ ก่อนแก้** — คอมเมนต์ในโค้ดอธิบาย "ทำไม" ไว้ละเอียด หลายจุดมาจากบั๊กที่เคยเจอจริง
6. **เขียนให้คนอ่าน** — อ่านง่าย แก้ง่าย เข้าใจง่าย เหมือนคนเขียนให้คนอ่าน ไม่ใช่เขียนให้เครื่องหรือเขียนอวดฝีมือ (หัวข้อ 7.1)

## 3. Backend (JavaScript CommonJS, Express 4)

### 3.1 ชั้นของโค้ด
| ชั้น | หน้าที่ | ห้าม |
|---|---|---|
| route | เส้นทาง + middleware สิทธิ์ตามลำดับ | มี logic |
| controller | ดึงค่าจาก `req` → ตรวจข้อมูล → เรียก service → ตอบ | เขียน SQL (โมดูลใหม่) |
| service | กติกาธุรกิจ, SQL, transaction · รับ `conn` เป็นพารามิเตอร์ให้เรียกต่อกันใน transaction เดียวได้ | แตะ `req`/`res` |

```js
// controllers/quotation.controller.js
async function approve(req, res, next) {
    try {
        const body = validate(approveSchema, req.body);
        const result = await withTransaction((conn) => quotationService.approve(conn, req.params.id, req.user, body.version));
        res.json(result);
    } catch (err) {
        next(err);
    }
}

// services/quotation.service.js
async function approve(conn, quotationId, approver, version) {
    const [[quotation]] = await conn.query("SELECT * FROM tb_quotations WHERE qt_id = ? FOR UPDATE", [quotationId]);
    if (!quotation) throw new AppError(404, "QUOTATION_NOT_FOUND", "ไม่พบใบเสนอราคานี้");
    if (quotation.qt_status !== "pending_approval") {
        throw new AppError(409, "QUOTATION_STATUS_CHANGED", "ใบนี้ไม่ได้อยู่ในสถานะรออนุมัติแล้ว (อาจมีคนอนุมัติ/ตีกลับไปก่อน) กรุณาโหลดหน้าใหม่");
    }
    // ...
}
```
- `withTransaction(fn)` ที่เดียว: begin → commit / rollback → release เสมอ (ไม่เขียน try/finally ซ้ำทุกที่) — สร้างตอนเริ่ม 1A
- controller ทุกตัวเป็น `async (req, res, next)` + `try/catch` ส่ง `next(err)` (Express 4 ไม่จับ error ของ async เอง)
- ฟังก์ชันกลาง (utils/services) เขียน **JSDoc** บอกพารามิเตอร์และค่าที่คืน — แทนชนิดข้อมูลที่ไม่มีใน JavaScript

### 3.2 Route และสิทธิ์
- ลำดับ middleware: `requireAuth` → `requirePermission(...)` → middleware ของโปรเจกต์ → controller
- **ทุก endpoint ที่เปลี่ยนข้อมูลต้องมีบิตสิทธิ์คุม** — การซ่อนปุ่มฝั่งหน้าเว็บไม่ใช่การกันสิทธิ์
- id ใน URL ต้องตรวจว่าอยู่ในขอบเขตที่อ้างจริง กันเข้าถึงข้ามกัน
- จัดการผู้ใช้/role: ใช้กติกา "สิทธิ์ไม่เกินตัวเอง" ผ่าน `utils/role-access.js` เสมอ
- `GET` แบบรายการ: `limit` (สูงสุด 200), `offset`, `search` → `{ data, total }`

### 3.3 Error
รูปแบบเดียวทั้งระบบ — โมดูลใหม่สร้างด้วย `throw new AppError(status, code, message, fields)` แล้ว error middleware จัดรูปแบบ (โค้ดเดิมตอบ `{ message, code }` ตรงๆ ได้)
```json
{ "message": "ข้อมูลไม่ถูกต้อง 1 ช่อง", "code": "VALIDATION", "fields": { "client_tax_id": "เลขผู้เสียภาษีต้องมี 13 หลัก" }, "request_id": "a1b2c3" }
```
- `message` ภาษาไทย บอก **ทำไม + ต้องทำอะไรต่อ** — ไม่ใช่ "เกิดข้อผิดพลาด"
- `code` ตัวพิมพ์ใหญ่-ขีดล่าง (`ROLE_IN_USE`) — หน้าเว็บตัดสินใจจาก `code` ไม่เทียบข้อความ
- `fields` = ผิดที่ช่องไหน (ชื่อตามคอลัมน์) ให้หน้าเว็บแสดงใต้ช่องนั้น
- รหัสสถานะ: `400` ข้อมูลผิด · `401` ไม่ได้ login · `403` ไม่มีสิทธิ์ · `404` ไม่พบ · `409` สถานะไม่ตรง/ซ้ำ/ถูกใช้งานอยู่/มีคนแก้ไปก่อน · `429` ถี่เกิน · `503` ระบบภายนอก/DB ยังไม่พร้อม · `500` บั๊กจริงเท่านั้น (ข้อความกลาง + request_id ไม่เผยรายละเอียดภายใน)

### 3.4 ตรวจข้อมูล (zod)
- schema อยู่ใน `shared/schemas/<โมดูล>` — ข้อความผิดพลาดภาษาไทยใน schema เลย
- backend: `validate(schema, data)` → ไม่ผ่าน = 400 `VALIDATION` + `fields` · ห้ามใช้ `req.body` ที่ยังไม่ผ่านการตรวจ
- frontend: ใช้ schema เดียวกันตรวจตอนกรอก แสดงใต้ช่องทันที (backend ตรวจซ้ำเสมอ)
- โค้ดเดิมที่ตรวจด้วยฟังก์ชัน `parseXxx(body)` ใช้ต่อได้ — ย้ายมาใช้ zod เมื่อแก้โมดูลนั้น

### 3.5 SQL
- `mysql2` + parameterized (`?`) เสมอ · ชื่อคอลัมน์ที่มาจาก input ต้องผ่าน whitelist ห้ามต่อสตริง
- `DECIMAL` ได้มาเป็น **string** (ห้ามแปลงเป็น number) · `DATE` ได้มาเป็น Date ที่ต้องอ่านผ่าน `bangkok-time` (หัวข้อ 3.7)
- หลายตาราง = transaction · เปลี่ยนสถานะ = `SELECT ... FOR UPDATE` · ร่างที่หลายคนแก้ได้ = optimistic lock (`*_version`) → 409
- คำนวณหนักทำใน SQL ครั้งเดียว ไม่ query ในลูป

### 3.6 ID และเลขที่เอกสาร
- ข้อมูลหลัก: `generateDailyId(table, column, PREFIX)` → 18 ตัว · ตาราง log: `BIGINT AUTO_INCREMENT`
- เลขที่เอกสาร: `issueDocumentNumber(conn, "QT", date)` **ใน transaction เดียวกับการบันทึก** · ห้ามสร้างเลขเอง

### 3.7 วันที่และเวลา
- **ห้ามใช้ `getFullYear()/getMonth()/getDate()/getHours()` ของเครื่อง** — production อาจเป็น UTC → วันที่เลื่อน 1 วัน
  ใช้ `utils/bangkok-time.js` ที่เดียว (มีเทสต์สแกนกันไว้) · ใน SQL ใช้ `CURDATE()`/`NOW()` ได้ (session เป็น +07:00)
- วันที่ไม่มีเวลาส่ง/รับเป็นสตริง `YYYY-MM-DD`

### 3.8 เงิน
- **ห้ามคำนวณเงินด้วย number ธรรมดา** — ผ่าน `money` ใน shared เท่านั้น (BigInt หน่วยย่อย, ปัดครึ่งขึ้น, ทศนิยมตามสกุลเงิน)
- เก็บ `DECIMAL(15,2)` · ส่งใน API เป็นสตริง `"1234.50"`
- backend คำนวณใหม่ทุกครั้งที่บันทึก · หน้าเว็บใช้ `money` ตัวเดียวกัน (จาก shared) จึงได้ยอดเท่ากันเสมอ
- **ยอดเงินบนเอกสาร/หน้าจอ: ชัดเจน ห้ามผิด ห้ามซ้ำซ้อน** (เจ้าของระบบสั่ง 17 ต.ค. 2026)
  - หนึ่งความหมาย = หนึ่งตัวเลข — ห้ามมี "ยอดที่ต้องจ่าย/ยอดสุทธิ" สองยอดที่อ่านแล้วเข้าใจว่าเป็นยอดจ่ายได้ทั้งคู่
  - ยอดที่เท่ากับบรรทัดถัดไปไม่พิมพ์ซ้ำ (เช่น รวมเป็นเงิน = รวมทั้งสิ้น เมื่อไม่มีส่วนลด/VAT · คอลัมน์ยอดเต็มเมื่อจ่ายเต็มทุกรายการ)
  - ส่วนสรุปอ่านเป็นการบวกลบจากบนลงล่างได้เสมอ ผู้อ่านไม่ต้องคิดเอง · ทุกยอดที่คิดจากฐานอื่นบอกฐาน (เช่น "ของยอดคงค้าง", "(ประมาณ)")
  - ตัวหนังสือ (บาทถ้วน) = ยอดหลักของเอกสาร (รวมทั้งสิ้น/รวมรับชำระ/ยอดตัดหนี้รวม) · ยอดหลังหัก ณ ที่จ่ายเป็นตัวเลขเท่านั้น · QR = บรรทัดยอดชำระสุทธิตัวหนาเสมอ
  - รับ/จ่ายบางส่วน: แสดงใบที่รับแล้วทุกใบ + คงค้าง · ใบที่ยกเลิกไม่นับ · ยอดคงค้างบนใบเสร็จเป็นยอด ณ ใบนั้น (พิมพ์ซ้ำได้ยอดเดิม)
  - แก้หน้าพิมพ์แล้วต้องถ่ายภาพและบวกเลขตรวจด้วยมือก่อนส่งมอบ

### 3.9 สิทธิ์ (bitmask)
- ลำดับบิตอยู่ที่ `utils/permissions.js` (ย้ายเข้า shared ตอนเริ่ม 1A) · **เพิ่มต่อท้ายเท่านั้น**
- เพิ่มบิต = แก้ backend + `frontend/app/components/bit.tsx` ให้ตรงกัน + เลขใน `RPAD` ของ role ระบบใน `deploy_schema.sql` · backend ตรวจความยาวตอนบันทึก role
- role ระบบได้สิทธิ์ครบทุกข้อเสมอ (`effectiveRolePermission`) · จัดการผู้ใช้/role ได้เฉพาะที่สิทธิ์ไม่เกินตัวเอง

### 3.10 เอกสาร, การลบ, ไฟล์
- **ร่างแก้ได้ · ออกแล้วแก้ไม่ได้** (ยกเลิกพร้อมเหตุผล / revision / เอกสารใหม่) · **snapshot ตอนออก** · อัตราต่างๆ มี "วันที่มีผล"
- ลบ: เช็กการอ้างอิงก่อน → 409 บอกว่าติดอะไร + แนะนำปิดใช้งาน · ข้อมูลที่เคยอยู่ในเอกสาร/มีประวัติ ใช้ `inactive`

### 3.11 Audit log และความลับ

## 4. ฐานข้อมูล
- **ทุกการเปลี่ยนโครงสร้างต้องแก้ `database/query/deploy_schema.sql`** ตามกติกาในหัวไฟล์ + แก้ `create_*.sql`
  แล้วรัน **`npm run schema:manifest`** (backend) ให้การตรวจโครงสร้างตอนเริ่มระบบรู้จักของใหม่ — ลืม = เทสต์ล้ม
- ทดสอบในฐาน `tmp_schema_*`: ฐานว่าง + ฐานเดิม + รันซ้ำ → ส่วนตรวจสอบท้ายไฟล์ได้ 0 แถว
- คิดถึง **ข้อมูลเดิมบน production** เสมอ: คอลัมน์ใหม่ NOT NULL ต้องมี default/เติมค่าแถวเดิม
- ตั้งชื่อ: ตาราง `tb_` พหูพจน์ · คอลัมน์มี prefix ของตาราง (`qt_status`) · เวลา `*_created_at`/`*_updated_at`/`*_at` · `idx_`/`uq_`/`fk_`
- `utf8mb4_unicode_ci` · InnoDB · สถานะ `ENUM` · เงิน `DECIMAL(15,2)` · อัตรา `DECIMAL(5,2)` · อัตราแลกเปลี่ยน `DECIMAL(20,10)` (บาทต่อ 1 หน่วย — สกุลที่ประกาศต่อ 1000 หน่วยต้องการ 10 ตำแหน่ง) · `COMMENT` คอลัมน์ที่ความหมายไม่ชัด

## 7. สไตล์โค้ด

### 7.1 เขียนให้คนอ่าน (สำคัญที่สุดในหัวข้อนี้ — เจ้าของระบบสั่ง 12 ต.ค. 2026)
โค้ดชุดนี้ต้องอยู่ 20 ปี คนที่แก้ในอนาคตไม่รู้บริบทวันนี้ **เกณฑ์: คนที่ไม่เคยเห็นไฟล์นี้ อ่านฟังก์ชันหนึ่งแล้วเข้าใจภายใน 1 นาที และแก้กติกาธุรกิจหนึ่งข้อได้โดยแตะที่เดียว**

**1. ชื่อบอกความหมาย ไม่ย่อ**
- `quotation`, `approvalLevel`, `amountBeforeVat` — ไม่ใช่ `q`, `lv`, `amt`, `r`, `tmp`, `data2`
- ข้อยกเว้น: `i` ในลูปสั้นๆ และชื่อคอลัมน์ฐานข้อมูล (`qt_status`) ที่ต้องตรงกับตาราง
- boolean ขึ้นต้นด้วย `is` / `has` / `can` (`isFinalLevel`, `canApprove`) · ฟังก์ชันชื่อเป็นกริยา (`issueNumber`, `calculateVat`)

**2. หนึ่งบรรทัดทำเรื่องเดียว**
```js
// ❌ อัดหลายคำสั่งในบรรทัดเดียว (เคยเขียนแบบนี้ในโค้ดร่าง ERP — จะแก้ตอนแปลงเป็น TS)
if (r.affectedRows === 0) { await conn.rollback(); return res.status(404).json({ message: "ไม่พบบัญชีนี้" }); }

// ✅
if (result.affectedRows === 0) {
    throw new AppError(404, "BANK_ACCOUNT_NOT_FOUND", "ไม่พบบัญชีธนาคารนี้ อาจถูกลบไปแล้ว กรุณาโหลดหน้าใหม่");
}
```
- ห้าม ternary ซ้อน (`a ? b : c ? d : e`) — ใช้ `if` หรือ `switch`

**3. ออกจากฟังก์ชันให้เร็ว แทนการซ้อน if ลึก** (ซ้อนไม่เกิน 3 ชั้น)
```js
// ❌ งานจริงจมอยู่ชั้นที่ 4
if (quotation) {
    if (quotation.qt_status === "pending_approval") {
        if (approver.user_id !== quotation.qt_created_by) {
            // ... งานจริง
        }
    }
}

// ✅ เช็กกรณีที่ไม่ผ่านก่อน งานจริงอยู่ระดับบนสุด
if (!quotation) {
    throw new AppError(404, "QUOTATION_NOT_FOUND", "ไม่พบใบเสนอราคานี้");
}
if (quotation.qt_status !== "pending_approval") {
    throw new AppError(409, "QUOTATION_STATUS_CHANGED", "ใบนี้ไม่ได้รออนุมัติแล้ว กรุณาโหลดหน้าใหม่");
}
if (approver.user_id === quotation.qt_created_by) {
    throw new AppError(403, "SELF_APPROVAL_NOT_ALLOWED", "คุณอนุมัติใบที่ตัวเองสร้างไม่ได้");
}
// ... งานจริง
```

**4. ฟังก์ชันสั้น ทำเรื่องเดียว อ่านจากบนลงล่างเหมือนเล่าเรื่อง**
ฟังก์ชันหลักเรียงขั้นตอนเป็นภาษาคน รายละเอียดอยู่ในฟังก์ชันย่อยที่ชื่อบอกว่าทำอะไร
```js
async function approve(conn, quotationId, approver) {
    const quotation = await lockQuotation(conn, quotationId);
    assertCanApprove(quotation, approver);

    const passedLevels = findLevelsApproverCanPass(quotation, approver);
    await recordApprovals(conn, quotation, passedLevels, approver);

    if (isFinalLevel(quotation, passedLevels)) {
        await issueApprovedQuotation(conn, quotation, approver);
    }
}
```
- ถ้าต้องเขียนคอมเมนต์ว่า "ส่วนนี้ทำ X" → แยกเป็นฟังก์ชันชื่อ X แทน
- ความยาวพอดีคือเห็นทั้งฟังก์ชันในจอเดียว (~40 บรรทัด)

**5. ชัดดีกว่าฉลาด**
```js
// ❌ ต้องหยุดคิดว่าทำอะไร
const req = lv.map((_, i) => i).filter((i) => amt >= lv[i].min);

// ✅ อ่านแล้วรู้เลย
const requiredLevels = approvalLevels.filter((level) => amountBeforeVat >= level.min_amount);
```
- ไม่ใช้ลูกเล่น (`!!x`, `~~x`, `reduce` ซับซ้อน, regex ยาวที่ไม่มีคำอธิบาย) ถ้ามีวิธีตรงไปตรงมา
- เลือกวิธีที่นักพัฒนามือใหม่อ่านออก แม้จะยาวกว่า 2–3 บรรทัด

**6. ไม่มีตัวเลขหรือข้อความลอยๆ** — ตั้งชื่อให้บอกความหมาย
```js
// ❌
if (days < 1 || days > 365) { ... }

// ✅
const MIN_VALID_DAYS = 1;
const MAX_VALID_DAYS = 365;
if (days < MIN_VALID_DAYS || days > MAX_VALID_DAYS) { ... }
```
สถานะ/ประเภทใช้ค่าคงที่จาก `shared/` ไม่พิมพ์สตริงซ้ำหลายที่

**7. ไม่สร้างโครงซับซ้อนก่อนจำเป็น**
- เขียนตรงๆ ก่อน · ซ้ำ **3 ครั้ง** ค่อยรวมเป็นของกลาง
- ไม่ทำ "framework" ภายใน, factory ซ้อน factory, class ที่มีแค่ method เดียว
- ฟังก์ชันธรรมดา + object ธรรมดา เป็นค่าเริ่มต้น · ใช้ class เมื่อมีเหตุผลชัด (เช่น `AppError`)

**8. ตรวจที่ขอบ แล้วข้างในเชื่อชนิดข้อมูล**
- ตรวจ input ครั้งเดียวที่ทางเข้า (zod) → ข้างใน service ไม่ต้องเช็ก `null`/ชนิดซ้ำทุกบรรทัด
- ไม่ใส่ `try/catch` ทุกฟังก์ชัน — จับเฉพาะที่จะทำอะไรกับ error จริงๆ (rollback, แปลงเป็นข้อความที่ผู้ใช้เข้าใจ)

**9. พารามิเตอร์อ่านออกตอนเรียก**
```js
// ❌ true/false คืออะไร?
createProject(data, true, false);

// ✅
createProject(data, { addCreatorAsPm: true, sendEmail: false });
```

**10. ใช้ `const` และคืนค่าใหม่ แทนการแก้ค่าเดิม** — แก้ค่าในที่ (mutate) เฉพาะที่จำเป็นจริงและเห็นชัด

**11. คอมเมนต์อธิบาย "ทำไม" ไม่พูดซ้ำโค้ด**
```js
// ❌ เพิ่ม 1 ให้ seq
// ✅ ใช้ LAST_INSERT_ID(expr) เพราะคืนค่าเฉพาะ connection นี้ — สองคำขอพร้อมกันจะไม่ได้เลขเดียวกัน
```
- ไม่ทิ้งโค้ดที่ comment ปิดไว้ (ประวัติอยู่ใน git) · `TODO` ต้องมีวันที่ + เหตุผล + แผน

**12. ไฟล์ชนิดเดียวกันหน้าตาเหมือนกัน** — อ่าน service หนึ่งไฟล์แล้วเข้าใจทุกไฟล์
- ลำดับในไฟล์: import → ค่าคงที่ → ชนิดข้อมูล → ฟังก์ชันที่ export (ตัวหลักก่อน) → ฟังก์ชันช่วย
- JSX: ไม่ยัดเงื่อนไขยาวใน JSX — คำนวณเป็นตัวแปรหรือแยก component ก่อน `return`

**13. เทสต์อ่านเป็นประโยค**
```js
test("ผู้สร้างใบอนุมัติใบของตัวเองไม่ได้ เว้นแต่เปิดตั้งค่าอนุญาต", async () => { ... });
```
หนึ่งเทสต์ตรวจหนึ่งพฤติกรรม · เตรียมข้อมูล → ทำ → ตรวจ แยกเป็น 3 ช่วงชัดๆ

### 7.2 รูปแบบและเครื่องมือ
- **Prettier** (ตั้งค่าที่ root): 4 ช่องว่าง · `"` คู่ · มี `;` · trailing comma ทุกที่ · ความกว้าง 120 · `(x) =>` มีวงเล็บเสมอ · ปลายบรรทัด LF
- จัดรูปแบบ **เฉพาะไฟล์ที่แก้** (`npm run format:changed`) — ห้ามจัดไฟล์ที่ไม่ได้แตะ ประวัติ git จะได้ไม่ปนกัน
- `.gitattributes` บังคับ LF (เครื่องนี้ตั้ง `core.autocrlf=true` เคยทำให้ไฟล์กลายเป็น CRLF)
- ESLint: frontend ใช้ของ Next · backend ยังไม่มีตัวตรวจ (เพิ่ม ESLint backend ภายหลังถ้าเจ้าของระบบอนุมัติ) — เทสต์จึงสำคัญมาก
- ตั้งชื่อ: ตัวแปร/ฟังก์ชัน `camelCase` · ชนิด/component `PascalCase` · ค่าคงที่ `UPPER_SNAKE` · ไฟล์ `kebab-case` · ฟิลด์ข้อมูลตามคอลัมน์ DB (`qt_status`)

## 8. ภาษาและคอมเมนต์
- UI, ข้อความ error, คอมเมนต์: **ภาษาไทย** · ชื่อในโค้ด: อังกฤษ · ข้อความ commit: **อังกฤษ**
- คอมเมนต์อธิบาย **ทำไม** — กติกาธุรกิจใส่ที่มา + วันที่ เช่น `// ผู้ใช้เลือก 12 ต.ค. 2026: วันที่เอกสาร = วันอนุมัติชั้นสุดท้าย (sales-cycle R10)`
- เขียนให้เหมือนโค้ดรอบๆ: ความหนาแน่นของคอมเมนต์ การตั้งชื่อ สำนวน

## 10. Git และ deploy
- ทำงานบน **master** · commit เมื่อเจ้าของระบบสั่งเท่านั้น · ห้าม push / deploy / แก้ production เอง
- ⚠ `deploy.bat` commit **ทุกอย่าง** ใน `backend/ database/ frontend/` แล้วส่งขึ้น production — งานครึ่งๆ กลางๆ จะติดไปด้วย
  → ทุกครั้งที่ส่งมอบต้องบอกว่า **"พร้อม deploy"** หรือ **"ยังไม่พร้อม deploy เพราะ …"** · ถ้ายังไม่พร้อม ห้ามรัน `deploy.bat`
- ลำดับ deploy: `deploy_schema.sql` บน production → backend (NPM install → build → Restart) → frontend · เพิ่มบิตสิทธิ์ = ขึ้นพร้อมกัน
- **ห้าม build frontend บน Windows แล้วส่ง bundle** — ส่ง source ให้ Plesk build เอง
